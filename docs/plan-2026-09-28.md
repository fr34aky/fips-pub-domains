# Plan: spec for resolving public domains over fips (Nostr claim + optional DNS verify)

## Context

Design discussion (2026-09-27/28): a fips client, with or without Internet,
should resolve a public name like `www.example.org` to a fips npub:

1. Nostr lookup (addressable kind 371xx, `d=<domain>`, author == claimed
   server npub) → the domain's fips DNS server `npubxyz.fips`.
2. Optional verification: the same record in legacy DNS (SRV/TXT under
   `_fips…`), strongest with DNSSEC.
3. Ask `npubxyz` over the mesh for `www.example.org` → `CNAME npub1234.fips.`

The user's three follow-up points are settled as follows and go into the spec:

- **HTTPS not required:** fips authenticates the npub end to end, so the
  security of a lookup is exactly the security of the name → npub binding.
  That makes the verification order (local > verified/pinned > attested >
  unverified-refused) more important, not less. Practical caveat: a browser
  with HSTS for the name, or a secure-context web API, still demands `https://`;
  a server using the same name on both networks should also serve its
  certificate on the fips address.
- **UDP is enough; TCP only as fallback:** fips authenticates the source
  address, so UDP's usual spoofing problem does not exist here, and UDP saves
  a round trip over the mesh. Answers (CNAME + a few records) are far below the
  mesh's effective IPv6 MTU (~1200; EDNS0 buffer 1232). Server must still
  support TCP for truncated answers (TC bit), as RFC 7766 requires. SRV name:
  `_fips-dns._udp.<domain>`.
- **Browsers are never changed; the machine's resolver is:** a browser asks
  the OS resolver for A/AAAA and never for SRV. The gap closes by putting a
  fips-aware resolver in the OS path — on the phone the shim already sees all
  DNS of mesh apps; on a laptop fips would run a local forwarding resolver
  for all names (systemd-resolved `~.` on the fips link, or dnsmasq upstream).
  For a bound name it synthesizes the `fd…` AAAA and suppresses A and public
  AAAA (address sorting puts `fd00::/8` last). Known holes: browsers with
  their own DoH (Firefox TRR, Chrome "secure DNS with provider") bypass it —
  answering the canary `use-application-dns.net` with NXDOMAIN disables
  Firefox's automatic DoH; enterprise policies may override. Machines without
  fips cannot reach `fd…` anyway, so they need nothing.
- **New issue to design around: privacy.** Querying Nostr relays for every
  domain a browser visits hands the browsing history to relay operators.
  When online, check the legacy `_fips-dns` SRV first (the upstream resolver
  already sees that name) and go to Nostr only for names with a binding hint,
  when offline, or from a locally synced claim set.

## Deliverable (on approval)

A design document only — no code:
`docs/fips-domain-binding.md` in the fips2go repo, on a branch, as a PR
(fr34aky identity, no Claude attribution), for later upstreaming to fips.

Contents:
1. Goals / non-goals (no legacy DNS dependency for operation; DNS only as
   optional verifier; not replacing ICANN).
2. Event formats: claim (kind 37197, `d=<domain>`, author = server npub,
   tags: service port, optional DNSSEC chain), attestation (witness-signed
   "verified <domain> → <npub> at T"), zone/delegation record (server-signed
   fallback for step 3 when the server is offline).
3. Legacy records: `_fips-dns._udp.<domain> SRV 0 0 53 npub….fips.` (label = npub, exactly 63 chars).
4. Resolver algorithm and precedence: local hosts > DNS-verified/pinned >
   attested by k trusted npubs > DNSSEC-proof-in-event > unverified (refuse
   or flagged); conflict handling for multiple claims; caching, TTLs,
   negative cache, pin changes.
5. Step 3 wire protocol: DNS over UDP to the server's fips address port 53,
   TCP fallback on TC; answer as `CNAME npub….fips.` so the local resolver
   registers the identity (the node cannot route to an unknown `fd…`).
6. OS integration: phone (shim `dns.rs`), Linux (fips as forwarding resolver),
   A/AAAA synthesis and suppression rules, DoH-bypass caveats.
7. Security and privacy analysis (squatting, rollback, relay withholding,
   DNS spoofing without DNSSEC, browsing-history leak, HSTS).
8. Phasing: MVP (claim + SRV verify + pinning + CNAME, refuse unverified) →
   attestations → DNSSEC proofs.
